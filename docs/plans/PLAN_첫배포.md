## 📋 개요

### 무엇을 만드는가
코딩을 전혀 모르는 초보자(중장년·시니어 포함)에게 "AI와 함께 내 서비스를 만들고 배포하는" 온라인 강의를 파는 사이트.
단순 소개 사이트가 아니라 **결제까지 완결되는 커머스**다.

퍼널: `유입 → 랜딩(설득) → 무료 1강 신청(경험) → 결제 → 내 강의실(수강)`

### 성공 기준
- [ ] 방문자가 무료 1강을 신청하고 시청할 수 있다
- [ ] 방문자가 결제하고 즉시 강의를 볼 수 있다
- [ ] 구매하지 않은 사람은 영상에 접근할 수 없다
- [ ] 강의 추가가 DB 행 추가만으로 가능하다
- [ ] 법적 고지 페이지가 모두 존재한다
- [ ] 375px에서 어절 중간 잘림이 0건이다

### 2. 흰 글자를 코랄 버튼에 쓸 수 없다

같은 이유로 코랄은 크림 배경 위에서 **글자색으로 쓸 수 없다**(2.92:1). 배경색으로만 쓴다.
잉크 배경 위 액센트 글자는 밝은 `--ink-accent`(`#FF7A45`, 7.27:1)를 따로 뒀다.

### 3. Paperlogy는 저장소에 파일을 직접 넣어야 한다

죽은 CDN 주소를 심는 대신 **자체 호스팅 경로**(`public/fonts/paperlogy/Paperlogy-9Black.woff2`)로

지금도 헤드라인은 정상으로 보이고 배포도 막히지 않는다. 받는 방법은
`public/fonts/paperlogy/README.md`에 적어 뒀다. **오픈 전 처리 항목이다.**

### 4. Pretendard는 CDN이 아니라 자체 호스팅한다
`@fontsource/pretendard`는 굵기당 **766KB**(한글 전체)라 시니어·모바일 타겟에 너무 무겁다.
공식 `pretendard` 패키지의 동적 서브셋(굵기당 92조각)을 쓰면 브라우저가 실제로 쓰인 글자가 든
조각만(보통 수십 KB) 내려받는다. 다만 서브셋 파일이 굵기 3개 × 92개 = 276개라 커밋하면 저장소가 지저분해진다.
→ `scripts/setup-fonts.mjs`가 `prebuild`에서 `node_modules`에서 뽑아 `public/fonts/`에 생성하고,
그 산출물은 `.gitignore`에 넣었다. 버전은 `package-lock.json`에 고정되므로 결과는 항상 같다.

### 5. `html { font-size: 18px }`의 파급 효과
본문을 18px로 올리면 Tailwind의 모든 `rem` 값이 함께 12.5% 커진다.
덕분에 `h-11`(2.75rem)도 49.5px로 최소 터치영역 48px을 자동으로 넘는다.

## Phase 2 배운 점 (2026-09-03)

### 1. RLS만으로는 vimeo_id를 못 막는다 — 직접 확인했다
계획은 "RLS를 켜면 anon이 `lessons`를 못 읽는다"를 전제했다. 실제로 해 보니 틀렸다.

```
RLS 켬 + `for select using (true)` 정책  →  anon이 vimeo_id 8건 전부 읽음
```

**RLS는 '행'을 거르지 '컬럼'을 가리지 못한다.** 그런데 커리큘럼(제목·길이)은 공개해야 하니
행 자체는 열어 줘야 하고, 그러면 같은 행의 `vimeo_id`가 따라 나온다.
행을 막으면 커리큘럼이 안 보이고, 열면 영상 ID가 샌다 — 정책으로는 풀 수 없는 문제였다.

→ **컬럼 단위 `grant`** 로 해결했다. `vimeo_id`만 빼고 권한을 준다.
정책을 잘못 써도 권한이 없으면 못 읽는다. 정책보다 아래에 있는 방어선이다.

이게 이번 단계에서 가장 중요한 발견이다. TDD 순서(테스트 먼저)가 아니었으면
"RLS 켰으니 됐다"로 넘어가서 유료 영상이 통째로 샜을 것이다.

### 2. 이 프로젝트의 anon에는 기본 권한이 없었다
예전 Supabase는 `public` 스키마의 새 테이블에 `anon`·`authenticated` SELECT를 기본으로 줬다.
이 프로젝트는 아니다 (`REFERENCES`·`TRIGGER`·`TRUNCATE`만 있었다).
`service_role`조차 DML 권한이 없어 명시적으로 부여해야 했다.
→ 권한을 추측하지 말고 `information_schema.role_table_grants`로 확인하고 시작한다.

또 `rls_auto_enable()`이라는 이벤트 트리거가 걸려 있어 새 테이블에 RLS가 자동으로 켜진다.
Supabase가 관리하는 안전장치다.

### 3. 테스트 단언은 좁게 써야 한다
`vimeo_id` 컬럼 권한이 0건인지 보는 검사가 처음에 FAIL이 났다.
실제로 남아 있던 건 `REFERENCES`(외래키를 걸 수 있을 뿐 값은 못 읽는다)였고
보안에는 문제가 없었다. 단언이 넓어서 난 거짓 실패다.
→ `privilege_type in ('SELECT','INSERT','UPDATE')`로 좁혔다.
넓은 단언은 진짜 문제를 가리는 소음이 된다.

### 4. 권한을 좁히면 쿼리 작성법이 달라진다
- `lessons`를 `select *`로 조회하면 권한 오류다. 컬럼을 명시해야 한다.
- `leads`는 `anon`에게 `insert`만 줬으므로 넣은 뒤 결과를 돌려받을 수 없다.
  `.insert(row).select()`를 붙이면 `permission denied`가 난다.
  → Phase 4에서 신청 폼을 만들 때 바로 걸릴 지점이라 테스트로 고정해 뒀다.

### 5. 헤더에 로그인 상태를 넣으면 전 페이지가 동적이 된다
레이아웃에서 `getUser()`를 부르면 쿠키를 읽게 되어 랜딩까지 동적 렌더링이 된다.
클라이언트에서 확인하면 정적으로 둘 수 있지만, 헤더가 잠깐 틀린 상태로 보였다가 바뀐다.
시니어 사용자에게 깜빡임은 혼란이므로 동적 렌더링을 택했다.
Phase 7에서 Lighthouse 성능이 문제되면 다시 본다.

### 6. 이 환경에서 확인하지 못한 것
개발 환경의 네트워크 정책이 `*.supabase.co`(REST·Auth)를 막는다. MCP 채널만 열려 있다.
- **가능했던 것**: 마이그레이션 적용, 역할 전환(`set role anon`) 기반 RLS 검증,
  `auth.users`에 직접 넣어 트리거 검증 — 전부 실제 데이터베이스에서 실행했다.
- **불가능했던 것**: 브라우저로 실제 로그인 → 세션 유지 → 로그아웃 왕복.
  카카오 대시보드 설정도 아직이라 어차피 지금은 돌지 않는다.
  → 대시보드 설정 후 로컬에서 확인해야 하는 **유일한 미검증 항목**이다.

비로그인 상태로 `/my`에 가면 `/login?next=/my`로 307 리다이렉트되는 것은 확인했다.
Supabase에 닿지 못하면 `getUser()`가 null을 주므로 **막히는 쪽으로 실패한다** — 안전한 방향이다.

### 7. 리전이 시드니다
`ap-southeast-2`로 만들어졌다. 이용자가 국내이므로 서울(`ap-northeast-2`)보다 왕복이 100ms쯤 길다.
리전은 나중에 바꿀 수 없고 새 프로젝트로 옮겨야 한다.
지금은 실사용자·결제 데이터가 없어 옮기는 비용이 가장 싸다 —
마이그레이션을 순서대로 다시 적용하면 끝난다. 오픈 후에는 훨씬 비싸진다.

Phase 1에서 가격을 `lib/config.ts`에 뒀는데, Phase 2에서 DB에도 들어갔다.
두 곳에 있으면 언젠가 어긋나고, 어긋나는 순간 **화면에 보인 가격과 청구되는 금액이 달라진다**.

`config.ts`에는 DB에 없는 것만 남겼다: 브랜드·연락처·사업자정보·내비게이션.

### 2. 자동 검사가 눈으로 못 볼 것을 잡았다
Quality Gate를 스크립트로 옮기면서 세 가지가 걸렸다.

- **FAQ의 `+` 기호가 대비 2.68:1** — 액센트 코랄을 밝은 배경 위 글자색으로 썼다.
  Phase 1에서 "코랄은 크림 위에서 글자색으로 못 쓴다(2.92:1)"고 적어 뒀는데도 또 했다.
  사람이 규칙을 기억하는 것보다 검사가 막아 주는 편이 확실하다.
- **강의 목록의 제목 링크가 33px** — 목록에서 가장 중요한 탭 대상인데 최소 크기 미달이었다.
- **문장 속 링크까지 48px을 요구해 거짓 실패** — 처음 규칙이 너무 넓었다.
  WCAG 2.5.8도 인라인 링크는 최소 크기에서 빼 준다. 문장 중간 링크를 48px로 키우면
  줄 간격이 망가져 오히려 읽기 어려워진다. 규칙을 좁혔다.

Phase 2의 "테스트 단언은 좁게" 교훈과 같은 이야기다. 넓은 단언은 소음이 되고,
소음이 쌓이면 진짜 실패를 무시하게 된다.

### 3. 고정 헤더 + 앵커 = 제목이 가린다
`#curriculum` 같은 앵커로 이동하면 섹션 제목이 고정 헤더 밑으로 들어갔다.
`scroll-margin-top`으로 해결했다. 헤더를 고정으로 두는 순간 따라오는 문제인데
클릭해 보기 전까지는 안 보인다.

### 4. 이 환경에서는 화면을 확인할 수 없어 장치를 하나 뒀다
개발 환경의 네트워크 정책이 `*.supabase.co`를 막아 서버에서 데이터를 못 읽는다.
공개 페이지는 전부 DB 데이터로 그려지므로 화면 확인 자체가 불가능했다.

→ `USE_CONTENT_FIXTURES=1`일 때만 고정 데이터를 쓰는 길을 뒀다.
**운영 빌드에서는 켜지지 않는다** — `NODE_ENV !== "production"` 검사가 앞에 있다.
실제로 `npm start`(운영 모드)로 띄우니 고정 데이터를 거부하고
"Host not in allowlist" 오류를 냈다. 안전장치가 의도대로 동작하는 것을 확인했다.
따라서 화면 검증은 `npm run dev`에서 했다. DOM과 CSS는 같으므로 레이아웃 검사에는 문제가 없다.

⚠️ 시드 데이터를 고치면 `lib/fixtures/content.ts`도 같이 고쳐야 한다. 안 그러면 개발 화면과 실제가 어긋난다.

### 5. 법적 고지 3종은 초안이다
이용약관·개인정보처리방침·환불 규정을 작성했다. 전자상거래법의 청약철회 규정과
디지털콘텐츠 특례(가분적 콘텐츠의 미개시 부분은 철회 가능)를 참고했고,
랜딩 FAQ의 환불 설명과 어긋나지 않게 맞췄다.

**다만 법률 전문가 검토를 받지 않았다.** 환불 규정은 분쟁이 가장 자주 생기는 문서다.
판매 시작 전에 반드시 검토받아야 한다. 각 페이지 상단 주석과 README 체크리스트에 적어 뒀다.

### 6. `/free`는 아직 404다
랜딩의 주 CTA가 가리키는 곳인데 Phase 4에서 만든다. 배포 전에 반드시 채워야 한다.

## Phase 4 배운 점 (2026-09-04)

### 1. 로그인 없는 접근 통제를 어떻게 할 것인가
무료 1강은 로그인을 요구하지 않는다 — 목표 행동이 '가입'이 아니라 '신청'이고,
시니어에게 새 비밀번호를 만들게 하는 것 자체가 이탈 요인이다.
그래서 "신청한 사람"임을 증명할 수단이 필요했다.

**서명된 쿠키**로 풀었다. 설계에서 신경 쓴 것:
- 쿠키에 연락처를 그대로 담지 않는다. HMAC 해시를 담는다.
  브라우저에 남는 값에서 개인정보를 되돌릴 수 없어야 한다.
- 서명이 **만료 시각까지 덮는다**. 만료만 늘리면 서명이 깨진다.
- 서명을 확인한 **다음에** 만료를 본다. 순서가 반대면 위조된 표의 만료 시각을 믿게 된다.
- 어떤 이유로 막히든 `false` 하나만 돌려준다. 왜 막혔는지 알려 주면 위조에 힌트가 된다.

⚠️ 이 표는 남에게 넘길 수 있다. 무료 강의라 그 정도 위험은 감수한다.
돈이 걸린 유료 강의는 로그인 + `enrollments`로 막는다 (Phase 6).

### 2. 중복 신청을 오류로 처리하면 안 된다
같은 번호로 다시 신청하는 건 대부분 "표를 잃어버렸다"는 뜻이다.
여기서 "이미 신청하셨습니다" 오류를 내면 그 사람은 다시 안 온다.

`leads.phone`에 유일 제약이 걸려 있으므로 재신청은 SQLSTATE **23505**로 실패한다.
서버는 이 코드만 골라 **성공으로 처리하고** 접근권을 새로 발급한다.
`upsert`를 쓰지 않은 이유: anon에는 `insert` 권한만 있고 `update`가 없어서
`on conflict do update`가 통하지 않는다. 권한을 넓히는 대신 오류 코드를 읽는 쪽이 낫다.

### 3. 자동 검사가 또 자기 규칙을 고치게 했다
- **체크박스가 27px로 실패** — 상자 자체는 작지만 감싼 `label`이 54px 클릭 영역이다.
  검사가 잘못된 대상을 재고 있었다. `label` 크기로 판정하도록 고쳤다.
- **빈 `role=alert`가 걸림** — Next.js가 화면 낭독기용으로 넣는
  `#__next-route-announcer__`였다. 내 마크업이 아니다. 검사 범위를 폼 안으로 좁혔다.

Phase 3에 이어 또 한 번, 넓은 규칙이 거짓 실패를 만들었다.
검사는 '무엇이 진짜 문제인지'를 정확히 겨냥해야 소음이 안 된다.

### 4. 실패 경로를 실제로 확인했다
이 환경은 supabase.co가 막혀 있어 신청 저장이 반드시 실패한다.
덕분에 오히려 실패 경로를 실물로 확인할 수 있었다 —
정상 입력으로 제출했더니 크래시 없이
"잠시 문제가 생겼습니다. 조금 뒤에 다시 시도해 주세요."가 뜨고
서버 로그에 원인이 남았다. 사용자에게는 부드럽게, 로그에는 정확하게.

### 5. 아직 필요한 것
- **`SUPABASE_SERVICE_ROLE_KEY`** — `lessons.vimeo_id`는 anon·authenticated에
  컬럼 권한이 없어 서버 전용 클라이언트로만 읽는다. 키가 없으면 영상 자리에
  안내 문구가 뜬다(페이지는 정상 동작). 대시보드에서 받아 `.env.local`에 넣어야 한다.
- **실제 Vimeo ID** — 시드는 `TODO-VIMEO-ID-01` 자리표시다.
  `TODO-`로 시작하면 재생기가 '준비 중'으로 표시한다.
- **Vimeo 도메인 제한** — iframe 주소는 페이지를 볼 수 있는 사람에게 어차피 보인다.
  우리 도메인 밖에서 재생되지 않도록 Vimeo에서 막아야 진짜 보호가 된다 (Phase 6).

## Phase 5 배운 점 (2026-09-04)

### 1. 토스만으로는 금액 위변조를 못 막는다
처음에 놓칠 뻔한 지점이다. "토스가 금액을 검증하니 괜찮지 않나?"는 **틀렸다.**

공격은 단순하다. 99,000원짜리 강의를 사면서 결제창에 100원을 넣는다.
토스는 100원이 **실제로 결제됐으므로** 승인을 내준다. 토스 입장에서는 정상 거래다.
막을 수 있는 것은 우리 서버뿐이다.

그래서 흐름을 이렇게 짰다:
1. 결제를 시작하기 **전에** 서버가 DB 가격을 읽어 대기 주문을 만든다.
2. 승인 단계에서 클라이언트가 들고 온 금액을 **그 주문에 박아 둔 금액**과만 대조한다.
3. 어긋나면 **토스를 부르기 전에** 멈춘다. 부르고 나서 되돌리는 건 늦다.

테스트가 "거부되는가"뿐 아니라 **"토스를 아예 부르지 않는가"** 까지 단언하는 이유다.

### 2. 판단 로직을 의존성에서 떼어 냈다
`confirmPayment`가 저장소와 토스 게이트웨이를 **인터페이스로 받는다.**
그래야 데이터베이스도 토스도 없이 위변조 시나리오를 테스트할 수 있다.
결제는 이 프로젝트에서 가장 위험한 코드이므로 이 정도 분리는 값을 한다 —
실제로 이 환경에서 supabase.co도 토스도 못 부르는데 10개 시나리오를 전부 검증했다.

### 3. 트랜잭션이 아니면 최악의 상태가 남는다
주문 상태 변경과 수강권 발급을 애플리케이션에서 두 번 호출하면,
그 사이에 실패했을 때 **"돈은 냈는데 강의를 못 보는"** 상태가 남는다.
supabase-js로는 여러 문장을 묶을 수 없어 `complete_paid_order` 함수로 만들었다.
`for update`로 행을 잠그므로 동시 승인도 한 번만 처리된다.

환불도 같은 이유로 함수다. 돈을 돌려주고 강의는 계속 보게 두면 안 된다.

### 4. 중복 승인은 반드시 온다
토스가 같은 승인을 두 번 보내거나 사용자가 완료 화면을 새로고침한다.
두 번 승인하면 두 번 청구된다.
이미 `paid`인 주문은 토스를 다시 부르지 않고 그대로 성공으로 돌려주도록 했고,
토스 호출에는 주문번호를 `Idempotency-Key`로 넣었다.

### 5. 설정이 덜 된 상태도 사용자에게 보인다
키 없이 승인 API를 부르니 **내용 없는 500**이 나왔다.
설정이 덜 된 것은 사용자 잘못이 아니다.
`createPaymentDeps()`로 미리 확인해 503 + 한국어 안내로 바꿨다.
Phase 4의 "사용자에게는 부드럽게, 로그에는 정확하게"와 같은 원칙이다.

### 6. 아직 확인하지 못한 것
**실제 토스 결제 왕복.** 이 환경은 supabase.co와 외부 API가 막혀 있고
키도 아직 넣지 않았다. 확인한 것과 못 한 것을 나누면:

| 확인함 | 방법 |
|---|---|
| 금액 위변조 거부 (10가지) | 단위 테스트 |
| 승인·환불 트랜잭션, 중복 승인, 수강권 회수 | 실제 DB에서 SQL 검증 8개 |
| 동의 없이 진행 불가 | 단위 테스트 + 화면 잠금 |
| Secret Key 비노출 | 빌드 산출물 검사 |

| 못 함 | 필요한 것 |
|---|---|
| 테스트키로 실제 결제 왕복 | 토스 키 + service_role 키 |

→ Phase 7에서 키를 넣고 소액 실결제 후 취소로 확인한다.

## Phase 6 배운 점 (2026-09-04)

### 1. Next 15.5의 `forbidden()`은 403을 주지 않는다
계획서의 "미구매자 시청 접근 403"을 그대로 만들려고 `forbidden()`을 썼다.
`authInterrupts` 실험 플래그를 켜니 `app/forbidden.tsx`가 **화면은 제대로 뜨는데
상태 코드가 404**로 나왔다. 정적·동적 렌더링 모두, 개발·운영 빌드 모두 같았다.

유료 콘텐츠 차단은 "없는 페이지"가 아니라 "권한이 없다"여야 한다.
검색엔진과 모니터링이 그 차이를 읽는다.
→ **미들웨어에서 직접 403 응답을 돌려주도록** 바꿨다. 실험 플래그는 되돌렸다.

규칙이 두 곳(미들웨어·페이지)에 흩어지지 않도록 수강권 조회를
`lib/lessons/enrollment-query.ts` 하나로 모으고 양쪽이 그것을 부른다.
페이지의 확인은 이중 방어로 남겨 뒀다 — 미들웨어 설정이 바뀌어도 스스로 막아야 한다.

### 2. 순서 자체를 방어선으로 삼았다
`resolveLessonVideo`는 **수강권을 확인하기 전에는 영상 주소를 읽지 않는다.**
영상 주소를 먼저 가져와 놓고 나중에 자격을 보면 실수 하나로 유료 영상이 샌다.
그래서 테스트도 "거부되는가"가 아니라 **"영상 주소를 아예 조회하지 않는가"** 를 단언한다.
Phase 5의 "토스를 부르기 전에 멈춘다"와 같은 생각이다.

무료 공개 차시도 이 경로에서는 예외를 두지 않았다. 무료 1강은 `/free/watch`에 따로 있고,
여기서 예외를 만들면 규칙이 흐려진다. 흐려진 규칙의 틈으로 새 나간다.

### 3. 관리자 화면을 일부러 세션 권한으로 읽는다
`service_role`로 읽으면 RLS를 우회하므로, 관리자 정책에 구멍이 있어도
화면이 멀쩡히 동작해 버린다. 세션으로 읽으면 정책이 실제로 맞는지 화면이 증명해 준다.
쓰기(환불)만 `service_role`을 쓴다.

비관리자에게는 404를 준다. 403은 "여기에 관리자 화면이 있다"는 사실을 알려 준다.

### 4. 또 테스트 단언이 틀렸다
"일반 수강생은 남의 주문을 볼 수 없다"가 FAIL로 나왔는데,
알고 보니 **검사 대상 본인 이름으로 주문을 만들어 놓고** '남의 주문'이라 단언한 것이었다.
본인 주문이 보이는 건 정상 동작이다. 제3자 사용자를 만들어 고쳤다.

Phase 2(REFERENCES 권한), Phase 3(인라인 링크), Phase 4(체크박스·route announcer)에 이어
네 번째다. **검사가 무엇을 재고 있는지 매번 다시 확인해야 한다.**

### 5. 번들 유출 검사를 스크립트로 만들었다
"빌드 산출물 grep"을 손으로 했더니 `123456789`가 라이브러리의 `"0123456789"`
(base64 알파벳)에 걸려 거짓 실패가 났다.
`npm run check:bundle`로 옮기고 패턴을 좁혔다. 서버 전용 값 9종을 매번 같은 방식으로 본다.

### 6. 남은 것 — Vimeo 도메인 제한
**코드로 할 수 없는 마지막 한 조각이다.**
iframe 주소는 페이지를 볼 수 있는 사람에게 어차피 보인다.
수강권 확인은 "누가 그 페이지를 보는가"를 막을 뿐,
주소를 복사해 다른 곳에 붙이는 것은 **Vimeo에서 도메인 제한을 걸어야** 막힌다.
이걸 안 하면 지금까지의 접근 통제가 한 겹 얇아진다. 오픈 전 필수 항목이다.

## Phase 7 전반부 배운 점 (2026-09-04)

### 1. 폰트 폴백이 페이지마다 404를 내고 있었다
Lighthouse 모범사례가 96에서 멈춰 원인을 보니 콘솔 오류였고,
그 정체는 **없는 Paperlogy 파일을 매 페이지 요청**하는 것이었다.

Phase 1에서 "파일이 없으면 Pretendard 900으로 자연 대체된다"고 해 두고 넘어갔는데,
화면이 멀쩡해 보여서 다섯 단계 동안 눈치채지 못했다.
폴백이 동작한다는 것과 요청이 낭비되지 않는다는 것은 다른 이야기였다.

→ `@font-face` 자체를 **파일이 있을 때만** 생성하도록 폰트 스크립트를 고쳤다.
없으면 규칙을 안 만드니 요청도 없고, 나중에 파일을 넣으면 자동으로 잡힌다.
모범사례가 100이 됐다.

### 2. 사이트맵이 쿠키 때문에 강의를 잃고 있었다
빌드 로그에 "Route /sitemap.xml couldn't be rendered statically because it used `cookies`"가 떴다.
공개 콘텐츠를 **세션 클라이언트**로 읽고 있었기 때문이다.

강의·커리큘럼·후기·FAQ는 로그인 여부와 무관하게 같은 내용인데,
세션 클라이언트를 쓰면 쿠키에 손을 대게 되고 그 페이지는 무조건 동적이 된다.
사이트맵은 그래서 빌드 시점에 만들어지지 못하고 강의 주소가 통째로 빠졌다.

→ 쿠키를 읽지 않는 `createPublicClient()`를 만들어 `lib/content.ts`가 그것을 쓰게 했다.
사이트맵이 정적으로 생성된다. 권한은 그대로 anon이고 RLS가 정한다.

### 3. JSON-LD에 별점을 넣지 않았다
후기가 전부 샘플인 동안 `aggregateRating`을 넣으면
검색 결과에 가짜 별점을 띄우는 셈이다. 구글은 이를 스팸으로 보고,
표시광고법 문제이기도 하다. 실제 후기가 모인 뒤에 넣는다.

### 4. 공유 카드 이미지는 미리 만들어 커밋했다
Next의 `ImageResponse`(satori)는 **woff2를 읽지 못한다.** 우리 본문 폰트가 woff2다.
한글 글꼴을 ttf로 따로 구해 런타임에 들고 있어야 하는데 그만한 값을 못 한다.
Chromium으로 한 번 그려 PNG로 커밋했다 — 배포 환경의 폰트 상황과 무관하게 항상 같다.

### 5. 시크릿 스캔은 이력까지 본다
지금 파일만 보면 부족하다. 한 번 커밋된 비밀값은 지워도 이력에 남고 그것으로 털린다.
`git rev-list --all`로 전체 이력을 훑는다.
지금은 변수 **이름**만 소스에 있고 실제 키 형태의 값은 0건이다.

### 6. 성능 점수는 여기서 재지 않았다
개발 서버는 번들이 압축되지 않고 최적화도 꺼져 있어 성능 점수가 실제와 크게 다르다.
접근성·SEO·모범사례는 DOM 기반이라 개발 서버에서도 의미가 있어 측정했고 셋 다 100이다.
**성능은 배포 후 실제 주소에서 재야 한다.**

## Phase 7 배포 시도 배운 점 (2026-09-04)

### 7. 빌드가 성공해도 배포는 실패할 수 있다
환경변수를 다 넣자 빌드는 끝까지 통과했다 —
컴파일, 타입, 린트, 페이지 데이터 수집, 정적 페이지 22개 생성,
`Build Completed in /vercel/output [58s]`까지 갔다.
그리고 `Deploying outputs...`에서 실패했다.

```
The Edge Function "middleware" is referencing unsupported modules:
	- __vc__ns__/0/middleware.js: @/lib/supabase/middleware
```

Vercel 오류 코드는 `NOW_SANDBOX_WORKER_EDGE_FUNCTION_UNSUPPORTED_MODULES`.
빌드 로그의 마지막 줄만 보면 "빌드 완료"라서 성공한 줄 알기 쉽다.
**배포 상태(state)를 따로 봐야 한다.** 로그는 빌드 이야기만 한다.

### 8. 첫 진단이 틀렸다 — 그리고 배포가 그것을 증명했다
`--turbopack`이 미들웨어를 조각 3개로 내는 것을 보고
"Vercel이 그 조각들을 합치다 경로를 잃는다"고 판단해 `--turbopack`을 뺐다.
근거도 있었다. 기본 빌드는 `server/middleware.js` 하나로 나오고,
두 경우 모두 바깥을 참조하는 모듈은 `node:async_hooks`·`node:buffer`뿐이었다.

**틀렸다.** 기본 빌드로 배포해도 같은 오류가 글자 하나 다르지 않게 그대로 났다.
산출물이 달라졌는데 오류가 그대로라면, 오류는 그 산출물에서 나온 것이 아니다.
그 사실이 오히려 진짜 원인을 가리켰다.

"직접 빌드해서 산출물을 열어 봤다"는 것만으로는 부족했다.
내가 확인한 것은 **Next가 만든 산출물**이지 **Vercel이 배포한 산출물**이 아니었다.
확인의 범위를 결론의 범위로 착각한 것이다.

### 9. 진짜 원인은 `@/` 별칭이었다
문제의 이름 `@/lib/supabase/middleware`는 뿌리 `middleware.ts`의
**유일한 `@/` 별칭 import**다. `@/`는 `tsconfig.json`의 `paths`가 정하는 우리 규약이고
Next는 이것을 푼다. 하지만 Vercel이 뿌리의 `middleware.ts`를 자기 방식으로 번들할 때는
`paths`를 보지 않는다. `__vc__ns__`는 Next의 산출물 이름이 아니다.

프로젝트가 옛날 정적 페이지 시절에 만들어져 **프레임워크 설정이 비어 있었다**(`framework: null`).
Next 프로젝트라고 알려 주지 않았으니 Vercel이 자기 규칙으로 처리한 것이다.

→ `vercel.json`에 `"framework": "nextjs"`를 명시하고,
뿌리 `middleware.ts`의 import를 상대 경로로 바꿨다.
누가 번들하든 풀리는 경로여야 한다. 파일에 왜 그런지 주석으로 남겼다.
`--turbopack`은 원인이 아니었으므로 되돌렸다.

### 10. 대시보드 설정도 저장소에 적어 둔다
`framework: null` 같은 값은 화면 어딘가에만 있으면 아무도 다시 보지 않는다.
`vercel.json`에 적어 두면 저장소가 스스로 말하고, 프로젝트를 다시 만들어도 따라온다.

## Phase 7 성능·공유카드 배운 점 (2026-09-05)

### 11. 카카오톡에 링크를 붙이면 빈 카드가 나갔을 것이다
성능을 재러 들어갔다가 SEO 점수가 91인 것을 보고 따라간 끝에 나온 문제다.

Next 15는 메타데이터(제목·설명·공유 카드)를 `<head>`에 넣지 않고 본문 뒤로
흘려보낸 다음 브라우저의 자바스크립트가 `<head>`로 끌어올린다.
사람에게는 화면이 더 빨리 떠서 좋다. 문제는 **자바스크립트를 실행하지 않는
미리보기 봇**이다. 그들에게는 `<head>`가 텅 빈 채로 보인다.

배포된 사이트에서 UA를 바꿔 가며 실제로 쟀다:

| 봇 | `<head>` 안 og 태그 | 제목 | 설명 |
|---|---|---|---|
| 페이스북·트위터·네이버 | 10개 | 있음 | 있음 |
| **카카오톡** | **0개** | **없음** | **없음** |

Next에는 "이 봇들에게는 완성된 HTML을 줘라"는 목록이 있는데 국내 서비스가 없다.
우리 손님은 카카오톡으로 링크를 주고받는다. 강의를 소개하는 링크가
제목도 가격도 이미지도 없는 빈 상자로 나갔을 것이다.
Phase 7에서 공유 카드 이미지를 애써 만들어 놓고 그것이 전달되지 않는 상태였다.

→ `next.config.ts`의 `htmlLimitedBots`에 카카오톡·다음·네이버·라인을 넣었다.
사람에게는 그대로 스트리밍하고 봇에게만 기다렸다 준다.

이건 **화면을 봐서는 절대 알 수 없다.** 카카오톡에 붙여 보기 전까지 모르고,
붙여 봤을 때는 이미 손님에게 빈 카드가 나간 뒤다.
그래서 `npm run check:preview`로 검사를 남겼다.
설정을 지우고 돌려 실패하는 것(RED)까지 확인했다 — 못 잡는 검사는 없는 것만 못하다.

**확인 (2026-09-05):** 배포된 주소를 실제 카카오톡 '나에게 보내기'에 붙여
제목·설명·이미지가 모두 뜨는 것을 확인했다.

이 확인이 중요한 이유 — 개발 환경은 `vercel.app`에 나가지 못해서
UA를 바꿔 가며 잰 것은 전부 **로컬 운영 빌드**였다. 배포된 사이트에서
카카오톡 봇이 실제로 어떻게 받는지는 확인할 방법이 없었다.
어제 로컬 산출물만 보고 `--turbopack`을 원인으로 짚었다가 틀린 일이 있어
"고쳤다"고 말하지 않고 카카오톡에서 눈으로 확인될 때까지 열어 뒀다.
**손님이 보는 자리에서 확인되기 전까지는 끝난 게 아니다.**

### 12. 남아 있던 서버가 옛날 빌드를 재게 했다 (여섯 번째다)
접근성이 100에서 96으로 떨어져 코드를 한참 뒤졌다.
원인은 앞선 실험에서 죽이지 않은 `next start` 8개가 포트를 잡고 있었던 것이다.
새 서버는 조용히 죽고, Lighthouse는 **옛날 빌드**를 쟀다.
CSS 파일 해시가 달라 400이 났고, 스타일 없는 화면의 점수가 나왔다.

이 프로젝트에서 "검사가 엉뚱한 것을 재서 가짜 실패가 나온" 일이 여섯 번째다.
→ 두 검사 모두 시작 전에 포트가 비었는지 확인하고, 이미 물려 있으면 멈춘다.

### 13. 이 기계의 숫자로 폰트 전략을 바꾸지 않는다
CLS가 0.172로 나왔다. 폰트를 차단하고 다시 재니 0이었다 —
Pretendard가 도착하면서 글자 크기가 바뀌어 본문이 밀리는 것이다.

하지만 고치지 않았다. `fc-list :lang=ko`로 확인해 보니 이 컨테이너에는
제대로 된 한글 글꼴이 없다(Unifont·WenQuanYi뿐). 대체 글꼴이 실제 손님 기기와
완전히 달라 밀림이 부풀려진 것이다.
Pretendard는 애플 SD 산돌고딕네오와 크기를 맞춰 만든 글꼴이라 실제 휴대폰에서는
훨씬 작게 나온다.

어제 `--turbopack`을 원인으로 짚었다가 틀린 것과 같은 함정이다.
**내가 잰 환경이 손님의 환경이 아니면, 그 숫자로 결정하지 않는다.**
검사 파일에 이 사실을 적어 두고, 실제 숫자는 배포 주소를 PageSpeed Insights에
넣어 받기로 했다.

### 14. 폰트가 요청 24개를 만든다 — 이건 기기와 무관하다
법률 페이지 하나에 폰트 파일 23개(약 300KB)와 40KB짜리 `fonts.css`가 붙는다.
그 CSS는 렌더를 막는 자원이라, CSS가 도착(186ms)한 **뒤에야** 폰트 요청이
시작된다(412ms). Phase 1의 "쓰인 글자가 든 조각만 내려받는다"는 선택에
이런 대가가 있다는 것을 이제야 쟀다.
실제 배포 주소의 숫자를 보고 판단한다.

## 카카오 로그인 KOE205 (2026-09-05)

### 15. 대시보드만 봐서는 답이 안 나오는 문제였다
카카오 개발자센터 설정은 멀쩡했다. 로그인 ON, 닉네임 필수 동의,
프로필 사진 선택 동의. 그런데 매번 KOE205였다.

우리 코드부터 봤다. `signInWithOAuth`에 **scope를 아예 넘기지 않는다.**
그러면 누가 scope를 정하는가 — Supabase다.
Supabase Auth의 카카오 제공자 소스를 읽었다
(`internal/api/provider/kakao.go`):

```go
oauthScopes := []string{
	"account_email",
	"profile_image",
	"profile_nickname",
}

if scopes != "" {
	oauthScopes = append(oauthScopes, strings.Split(scopes, ",")...)
}
```

`account_email`이 **코드에 박혀 있다.** 우리가 넘기는 scope는 덧붙기만 하고
지우지 못한다. 즉 카카오에 이메일을 요청하지 않는 방법이 없다.
카카오 앱에 그 동의항목이 없으면 영원히 KOE205다.

### 16. 내가 안내한 해결책이 문제의 원인이었다
나는 "이메일은 비즈 앱이 필요하니 건드리지 말고, 대신 Supabase의
`Allow users without an email`을 켜라"고 안내했다. **그게 KOE205를 만들었다.**

그 스위치는 `conf.OAuthProviderConfiguration.EmailOptional`이고
"이메일 **없는 사용자를 만들어도 되는가**"를 정한다.
"카카오에 이메일을 **요청할 것인가**"와는 다른 값이다.
이름이 비슷해서 같은 것이라고 넘겨짚었다.

두 값은 동작하는 시점도 다르다. 요청 scope는 카카오 동의 화면에 **가기 전에**
결정되고, `EmailOptional`은 돌아온 **다음에** 쓰인다.
카카오가 문 앞에서 막으니 뒤쪽 스위치는 켜져 있어도 쓰이지 않는다.

→ 실제 해결은 **비즈 앱 전환**이다. `account_email` 동의항목은 거기서만 열린다.

### 17. 오류 나는 버튼은 없느니만 못하다
비즈 앱 전환은 사업자 정보가 필요해서 바로 되지 않는다.
그동안 로그인 화면의 첫 버튼이 **누구에게나 실패하는** 상태로 남는다.

`NEXT_PUBLIC_KAKAO_LOGIN_ENABLED`를 만들었다. **기본값은 꺼짐이다.**
값을 안 넣으면 카카오 버튼이 나오지 않고 이메일 로그인이 첫 자리로 올라온다
(보조 버튼 모양이 아니라 주 버튼이 된다 — 그때는 그것이 유일한 길이므로).

기본값을 '켜짐'으로 두지 않은 이유 —
되는 줄 알고 켜 두는 것보다 안 되는 줄 알고 꺼 두는 쪽이 안전하다.
켜는 것은 한 줄이지만, 실패하는 버튼은 손님을 잃는다.

Phase 2에서 "카카오 심사가 늦어져도 막히지 않게" 이메일 폴백을 만들어 둔 것이
여기서 값을 했다. 결제도 수강도 그대로 된다.

## 이메일 로그인이 첫 화면으로 떨어진 이유 (2026-09-05)

### 18. 로그가 답을 갖고 있었다
"메일 링크를 눌렀는데 그냥 홈페이지가 열린다"를 두 번 겪었다.
첫 진단은 "Redirect URLs에 미리보기 주소가 없다"였는데,
확인해 보니 **이미 등록돼 있었다.** 가설이 틀렸다.

거기서 더 짐작하지 않고 Supabase 인증 로그를 봤다.
`/otp` 요청 두 건 모두 `referer`가 **Site URL**이었다 —
요청한 주소가 아니라 대체된 주소다. 거부되고 있었다는 뜻이다.

### 19. 등록돼 있는데도 거부된 이유는 물음표였다
Supabase 문서의 와일드카드 규칙:

> `*`는 구분자가 아닌 문자들의 연속에 대응한다.
> **URL의 구분자는 `.` 와 `/` 이다.**
> `http://localhost:3000/*`는 `/foo`에 맞지만 `/foo/bar`나 `/foo/`에는 맞지 않는다.

그리고 우리 로그인 폼이 만드는 주소:

```ts
`${window.location.origin}/auth/callback?next=${encodeURIComponent(path)}`
```

**`?next=...`가 뒤에 붙는다.** 등록값이 `.../auth/callback`으로 끝나면
물음표 뒷부분 때문에 대응하지 않는다. 목록에 있어도 거부된다.

→ 끝을 `/**`로 열어야 한다.

거부되면 Supabase는 **오류를 내지 않고 조용히 Site URL로 보낸다.**
이 조용함이 문제를 어렵게 만들었다. 화면만 봐서는 무엇이 거부됐는지 알 수 없다.

### 20. "확인했다"가 "맞다"는 아니다
사장님이 "두 주소가 이미 등록돼 있다"고 확인해 주셨을 때
나는 그 말을 **등록 = 유효**로 받아들이고 다른 원인을 찾으려 했다.
실제로는 등록돼 있었지만 형태가 틀려서 안 맞고 있었다.

값이 있는지와 값이 맞는지는 다른 질문이다.
확인을 부탁할 때는 **무엇을 보고 무엇을 판정해야 하는지**까지 적어야 한다.
"등록돼 있나요"가 아니라 "끝이 `/**`인가요"라고 물었어야 했다.

### 21. 절반만 된 상태가 가장 위험하다
DB를 보니 계정 생성·이메일 인증·프로필 트리거까지 전부 정상이었고
`last_sign_in_at`만 비어 있었다. 겉으로는 가입이 된 것처럼 보인다.
손님도 "가입은 됐는데 로그인이 안 되는" 상태에 빠진다.

화면·DB·로그를 각각 봐야 이게 보인다. 하나만 보면 성공으로 오해한다.

### 22. 이메일 로그인 왕복 성공 (2026-09-05)
Redirect URLs를 `/**`로 고치자 바로 됐다. 배포 환경에서 확인한 값:

| 항목 | 결과 |
|---|---|
| `/my` 진입 | ✅ 화면에 이메일과 인사말 |
| `auth.sessions` | 1건 |
| `last_sign_in_at` | 08:46:31Z 기록됨 |
| `profiles.role` | `student` |
| `enrollments` | 0건 — 아직 결제 전이니 맞다 |

Phase 2에서 "이 환경에서 실행 불가"로 남겨 뒀던 Quality Gate가
두 단계(로그인·세션 유지)까지 실제로 닫혔다. 로그아웃 왕복만 남았다.

`display_name`이 비어 있는 것도 정상이다 —
이메일 가입에는 이름이 없다. 카카오로 들어오면 닉네임이 채운다.
화면은 `display_name ?? email ?? "회원"` 순서라 이메일이 그 자리를 채우고 있다.

**교훈 하나 더 —** 진단이 두 번 틀렸다.
1) "Redirect URLs에 주소가 없다" → 있었다.
2) 그래서 로그를 봤고, 거기서 거부 사실이 드러났다.

화면만 보고 세 번 시도하는 것보다 로그를 한 번 보는 것이 빨랐다.
다음에 인증이 이상하면 **먼저 `auth_logs`의 `referer`를 본다.**
요청한 주소가 아니라 Site URL이 찍혀 있으면 거부된 것이다.

### 23. 로그아웃은 화면이 아니라 세션으로 확인했다
헤더가 "로그인"으로 바뀐 것만으로는 부족하다.
화면은 로그아웃된 것처럼 보이는데 서버에 세션이 살아 있으면,
그 표는 아직 유효하고 누군가 주워 쓸 수 있다. 그게 더 나쁘다.

DB로 확인한 값 (로그아웃 후):

| 항목 | 값 |
|---|---|
| `auth.sessions` | **0건** |
| 살아 있는 refresh token | **0건** |
| `last_sign_in_at` | 08:46:31Z 그대로 (기록이므로 남는 게 맞다) |

세션이 서버에서 실제로 회수됐다. Phase 2의 마지막 Quality Gate가 닫혔다.

Phase 2를 만들던 날에는 이 환경에서 supabase.co에 나갈 수 없어
"실행 불가"로 남겨 뒀던 항목이다. 미뤄 둔 검증은 잊히기 쉬운데,
계획서에 `[~]`로 남겨 둔 덕에 배포 뒤에 다시 찾아와 닫을 수 있었다.
